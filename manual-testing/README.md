# 📝 Артефакты ручного тестирования (Manual QA)

В данном разделе представлены примеры тестовой документации для функционала **«Корзина и Оформление заказа (Checkout)»** на сайте [SauceDemo](https://saucedemo.com).

## 🎯 Цель проекта

Продемонстрировать навыки применения техник тест‑дизайна, составления чек‑листов и создания понятных, детальных баг‑репортов. А также показать умение обосновывать объём тестирования и управлять рисками.

## 💼 Бизнес‑ценность тестирования

Фича Checkout напрямую влияет на конверсию и выручку:

* **Потеря заказов:** баги в корзине или валидации приводят к отказу от покупки.
* **Юридические риски:** некорректный расчёт итоговой суммы (без учёта налогов) может нарушать правила платформы и требования регуляторов.
* **UX‑репутация:** ошибки валидации или непонятные сообщения ухудшают доверие пользователя к магазину.

## 🧠 Использованные техники тест‑дизайна

| Техника | Применение | Пример кейса |
| -------- | ------------ | -------------- |
| **Эквивалентное разделение** | Группировка входных данных на валидные/невалидные классы. | Валидные строки (a–z, A–Z), спецсимволы, числа в текстовых полях. |
| **Анализ граничных значений** | Проверка крайних значений и переходов между классами. | Пустая строка, 1 символ, 255 символов, 256 символов. |
| **Предугадывание ошибок (Error Guessing)** | Тестирование «слабых мест» на основе опыта. | Прерывание сессии, дублирование вкладок, отключение сети на шаге оплаты. |
| **Сквозное тестирование (E2E)** | Проверка полного пользовательского сценария. | От выбора товара до экрана «Thank you for your order!». |
| **Таблица решений (Decision Table)** | Логика валидации полей (все поля заполнены/пустые/частично заполнены). | Комбинации валидных/пустых полей для проверки сообщений об ошибках. |

## ⚠️ Ограничения и допущения

* **Тестовые данные:** использовались стандартные учётные записи SauceDemo (`standard_user` / `password123`).
* **Окружение:** веб‑приложение без бэкенд‑интеграций (платежи — моковые).
* **Глубина тестирования:** фокус на клиентской валидации и UX. Проверка интеграции с платёжными шлюзами и БД не проводилась.
* **Приоритет:** высокий приоритет у кейсов, блокирующих покупку или искажающих итоговую сумму.

## 📈 Критерии приёмки (DoD) для фичи Checkout

Функционал считается протестированным и готовым к релизу, если:

* [ ] Пройдено 100% позитивных сценариев из чек‑листа.
* [ ] Протестированы граничные значения и негативные сценарии для всех полей ввода.
* [ ] Проверено соответствие итоговой суммы формуле: `Item total + Tax = Total`.
* [ ] Все найденные дефекты зафиксированы и имеют статус «Open» или «Fixed».
* [ ] Чек‑лист обновлён с отметками о прохождении (Pass/Fail).
